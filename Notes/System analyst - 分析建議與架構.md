# 系統分析：分析建議與架構

> 針對 `System analyst.md` 的初步構想，以系統分析師角度整理的需求缺口、風險與定案架構。
> 專案性質：授權範圍內、教育用途的紅隊攻防演練平台（cyber range）。

---

## 一、需求缺口（原筆記未提到但一定要補的）

1. **靶機 / 目標環境**：原筆記只描述「攻擊方的 Kali」，但攻防演練必須有被攻擊的目標（vulnerable targets）。**難度選擇 = 不同的靶場情境（scenario）**。這是最大缺口。
2. **使用者身分與帳號管理**：50 人需要登入、分組、Session 綁定。
3. **計分 / 進度 / 通關判定**：教育平台通常需要 flag、任務檢核、進度儲存。
4. **網路隔離拓撲**：50 人各自環境要互相隔離，且與外部網際網路隔離（防止平台被拿去打真實外部目標——這對「授權範圍」是法律與道德底線）。
5. **生命週期管理**：環境的建立、重置（reset）、逾時回收、清理。
6. **稽核與監控**：每個指令、AI 動作都要留 log（教育回饋 + 事故追蹤 + 濫用偵測）。
7. **資源預算**：50 併發是硬體規模的關鍵決策點（見第四節）。

## 二、風險 / 敏感點

- **AI 直接操作 Kali**：即使在授權環境，讓 LLM 執行任意指令仍需護欄——命令白/黑名單、每位使用者環境沙箱化、防止容器逃逸、防止對演練範圍外的網段/網際網路發動流量、完整稽核。
- **範圍外攻擊防護**：預設 egress 封鎖，只允許連到指定靶場網段。這是此類平台的第一優先。
- **50 併發的資源成本**：每位一台 Kali 容器（~1–2GB RAM）+ 靶機（~1–3GB）。50 人約需 150–250GB RAM 等級的資源，牽涉單機是否足夠。
- **AI 成本與速率限制**：50 人同時呼叫 LLM 的費用與 rate limit。

## 三、定案架構

**已確認決策：**
- 第一版於**單台伺服器、純 Docker** 快速上線。
- AI 後端使用**雲端 LLM API**。
- 團隊具備 K8s 能力，故**架構須保持「可平移到 K8s」**，日後再擴充。

### 元件

- **前端**：Web app（入口頁：專案名稱／簡介／難度選擇）+ `xterm.js` 終端機元件。
- **終端 Gateway**：WebSocket ↔ PTY，採用 `ttyd` / `wetty` 這類成熟方案（避免自造 PTY 橋接）。
- **編排層 (Orchestrator)**：一個控制平面服務（Node 或 Python）透過 **Docker Engine API** 動態建立「每人一組」的 Kali 容器 + 靶機。單機 → 用 Docker 網路，不需 K8s。
- **AI 服務（後端 Proxy）**：瀏覽器**絕不**持有 API key；由後端代理呼叫雲端 LLM，集中做 per-user rate limit、prompt 模板、**指令白/黑名單護欄**、以及完整稽核。AI 產生的指令透過 `docker exec` / PTY 在該使用者容器內執行；破壞性指令需可見確認。
- **情境 (Scenario) 定義**：每個難度 = 一份 `docker-compose`（Kali + 靶機 + 隔離網路），版本控管、可重置。
- **隔離與 egress**：每人獨立 Docker 網路；**預設封鎖對外網際網路**，只放行 (a) 該情境靶場網段，(b) 後端代理連往 LLM API 的白名單網域。使用者容器本身不得直連網際網路。

### 分階段策略（Docker → K8s）

- **Phase 1（現在）**：純 Docker（Docker Engine API + Compose）在單機出第一版。最快、Kali 權限好給、AI 用 `docker exec` 下指令最順。
- **Phase 2（日後）**：平移到 k3s/K8s，用宣告式 `NetworkPolicy` + `ResourceQuota` 取代手工 iptables，並可加節點水平擴充。

### 讓 Phase 2 平移成本最低的設計原則（Phase 1 就要做對）

- **編排抽象化**：把「建立／銷毀使用者環境」封裝成一個 `EnvironmentProvider` 介面，Phase 1 實作 Docker 版，Phase 2 換 K8s 版即可，上層不動。
- **情境宣告化**：每個難度用 `docker-compose` 定義，未來可用 `kompose` 或手工轉成 K8s manifest / Helm chart。
- **控制平面無狀態**：使用者／情境狀態放外部（DB／Redis），控制服務本身可隨時重啟或多副本。
- **隔離與 egress 先寫成規則文件**：Phase 1 用 Docker 網路 + iptables 實作，同時記錄等效的 `NetworkPolicy`，Phase 2 直接對應。

## 四、單機 50 併發的資源策略（關鍵）

- 使用**精簡版 Kali**（headless／自訂工具集），而非完整桌面版，壓低每容器 RAM。
- 每容器設 **CPU／RAM 上限**（`--cpus`, `--memory`），避免單一使用者拖垮全機。
- **按需建立 + 閒置回收**：使用者進場才起環境，逾時自動 reap；並非 50 個永遠常駐。
- 先做**資源試算與壓測**確認單機規格是否足夠（見第五節）。

## 五、驗證方式（開發後）

- **單使用者端到端**：入口頁選難度 → 建立 Kali+靶機 → Web 終端可操作 → AI 下達自然語言指令並在容器內執行 → 稽核 log 有紀錄。
- **隔離測試**：從 Kali 嘗試連外部網際網路應被封鎖；嘗試連其他使用者環境應失敗。
- **負載測試**：模擬 50 併發環境建立，量測 RAM／CPU 與建立延遲。
